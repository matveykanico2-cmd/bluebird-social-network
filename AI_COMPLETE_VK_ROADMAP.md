# BLUEBIRD — ЗАДАНИЕ ИИ-РАЗРАБОТЧИКУ: ДОВЕСТИ ПРОЕКТ ДО ПОЛНОЦЕННОЙ СОЦСЕТИ УРОВНЯ VK

> Этот файл — исполняемое техническое задание для coding agent (Codex / Cursor / GitHub Copilot). Сам по себе Markdown-файл не реализует функции: агент должен изменять исходный код, запускать тесты и фиксировать прогресс. Цель — полноценный собственный продукт Bluebird с UX-паттернами современной социальной сети ВКонтакте, а не использование логотипов, закрытого кода, чужих медиа или обманной формы входа VK.

Исходный репозиторий: `matveykanico2-cmd/bluebird-social-network`.

Реально существующая архитектура по состоянию на 2026-11-26:
- npm workspaces: `apps/web` (React + Vite + TypeScript), `apps/api` (NestJS + SQLite), `packages/shared`, `packages/contract-tests`;
- аутентификация с httpOnly cookie и регистрацией без обязательного подтверждения почты; друзья, профиль, лента, посты, реакции, комментарии, чаты Socket.IO, группы, поиск, уведомления и часть медиа уже реализованы;
- `apps/web/src/openvk-skin.css` — существующая визуальная тема, но это ориентир на старый VK; нужно современное оформление;
- существующая документация может противоречить сама себе: `FEATURE_MATRIX.md` местами отстаёт от `PROGRESS.md`, поэтому **истина — код + миграции/схема + запущенные тесты + ручная проверка**.

## 1. Конечная цель и критерии «полноценной соцсети»

Реализовать согласованную систему **фронтенд + API + БД + realtime + тесты + админка**. Разделы должны быть доступны по настоящим маршрутам и работать с реальными данными двух и более пользователей. Сохранение после перезагрузки обязательно.

### 1.1 Аккаунты и безопасность
- Регистрация по email или телефону без обязательного подтверждения при включённом режиме `AUTH_REQUIRE_VERIFICATION=false` (сохранить существующее поведение), вход и выход, безопасное восстановление доступа, смена пароля, управление сессиями.
- **Не допускать захвата аккаунта через «восстановление по одному email/телефону»:** сброс пароля разрешён только после проверки владения каналом, заранее созданных recovery codes или другого подтверждённого фактора. В dev разрешены только явные тестовые коды, никогда не возвращай их из production API.
- MFA/TOTP с backup codes: при включённой MFA проверять фактор на входе; запрет повторного использования кодов.
- Серверные права на все операции, владелец ресурса, роли, приватность, ограничения по запросам, безопасные cookies, CSRF-защита по схеме сессий, CORS allowlist, валидация входа, аудит критичных действий.
- Автозаполнение профиля, onboarding, блокировки, жалобы, чёрный список, экспорт и удаление данных.

### 1.2 Профили и друзья
- Страницы профилей с обложкой, аватаром, статусом, подробной информацией, собственной стеной и вкладками.
- Подписки, заявки, дружба, скрытые друзья и приватность постов/фото/профиля; проверять ACL даже при прямом запросе API.
- Альбомы, видео, клипы, музыка, общие друзья, подписчики, подарки/достижения (опционально), верификация через модератора.
- Поиск людей, рекомендации, онлайн-статус с настройками приватности.

### 1.3 Лента и посты
- Лента «Для вас», «Подписки», «Недавние» с cursor pagination и недублирующимися карточками.
- Полный жизненный цикл поста: создать, редактировать, удалить/архивировать, отложить, закрепить, сохранить в закладки, репостнуть.
- Несколько фото, видео, GIF, документы, опросы, ссылки с безопасным превью, геолокация, упоминания и хештеги.
- Реакции, просмотры, вложенные комментарии, ответы, жалобы, настройки аудитории; приватность проверяется на сервере.
- Никаких фейковых счётчиков, бесконечных фиктивных лент и кнопок «заглушек».

### 1.4 Мессенджер
- Прямые, групповые и тематические чаты; список диалогов, поиск, папки, архив, закрепление, mute.
- Socket.IO: реальные новые сообщения, доставлено/прочитано, online/typing, reconnect/resync, история с пагинацией.
- Ответ, пересылка, редактирование, удаление, реакции; голосовые сообщения и вложения — с безопасной загрузкой и воспроизведением.
- Участники, роли, приглашения, блокировки и разрешения; защита от доступа к чужим чатам.
- Аудио/видеозвонки через WebRTC; STUN/TURN и при необходимости SFU задаются через env, без обещаний, что всё заработает без инфраструктуры. Явная диагностика неподключённого провайдера.

### 1.5 Сообщества и каналы
- Создание сообщества, публичные и закрытые сообщества, вступление/заявка, роли владелец/админ/модератор/участник.
- Стена сообщества, расписание публикаций, закрепы, настройки комментирования, участники, приглашения, жалобы и модерация.
- Каналы публикаций/подписок с правами автора; подписки и уведомления.
- Приглашения и ссылки с истечением срока; безопасная обработка токенов.

### 1.6 Истории, клипы, видео, прямые эфиры
- Истории с TTL 24 часа, аудиториями, просмотром, реакциями, архивом, фото и короткими видео.
- Клипы: вертикальная лента, подписки, лайки, комментарии, просмотры, загрузка с ограничениями, постер, транскодирование.
- Видеокаталог: поиск, обложки, описание, загрузка, плейлист, публичность, адекватное воспроизведение.
- Медиа-пайплайн: проверка формата/реального содержимого, ограничения, strip EXIF, thumbnail, очереди FFmpeg, object storage (S3-совместимый или совместимый локальный dev adapter).
- Эфиры — только при реально установленном ingest/streaming stack; иначе обозначить как `blocked`, не подделывать работу.

### 1.7 Музыка
- Раздел аудио, плейлисты, очередь, плеер, избранное, поиск, карточка исполнителя.
- Только собственные/разрешённые записи или подключённый лицензированный источник. Без пиратского каталога и скачивания музыки VK.
- Защита прав доступа к медиа и ограничение доступа к файлам.

### 1.8 Дополнительные разделы
- Глобальный поиск по пользователям, постам, сообществам, видео, аудио с permission-aware результатами.
- Уведомления с deeplink, счётчиками, настройками типов и real-time delivery; push при наличии провайдера.
- Закладки с коллекциями и типами сущностей.
- Маркет: объявления, фото, категории, фильтры, продавец, карточка товара, переписка; платежи только при интеграции реального провайдера.
- События/мероприятия, опросы, рекомендации сообществ.
- Админ-панель: пользователи, жалобы, блокировки, контент-модерация, audit log, ограничения прав, настройки платформы. Роль администратора только через серверную настройку, никогда через выбор роли при регистрации.
- Политики приватности, правила сервиса, доступность клавиатурой, локализация RU/EN, понятные состояния ошибок.

## 2. Современный дизайн в стиле VK

Обновить визуальную систему на основе существующего React-кода, **сохраняя бренд Bluebird**. Вдохновляться современными UX-паттернами VK, но не копировать защищённые ассеты, логотипы или узнаваемые формы входа для сбора VK-паролей.

- Шапка с логотипом Bluebird, глобальным поиском, уведомлениями, сообщениями и профилем.
- Боковая навигация: Моя страница, Новости, Мессенджер, Друзья, Сообщества, Фото, Видео, Клипы, Музыка, Закладки, Маркет, Настройки.
- Центр: настоящая лента, композер, истории, карточки медиа; правая колонка: рекомендации/друзья/события.
- Desktop 1440px, laptop 1024px, mobile 390px и 360px; на mobile нижняя навигация и доступность элементов одним пальцем.
- Тёмная и светлая темы, дизайн-токены, единая библиотека компонентов, skeleton/loading/empty/error/toast, фокус и ARIA.
- Не менять весь CSS одним непроверяемым рефакторингом; сравнивать скриншоты и проверять регрессии.
- Не использовать по умолчанию чужие изображения/иконки, на которые нет прав. Допустимые open-source зависимости отмечать в `THIRD_PARTY_NOTICES.md`.

## 3. Архитектурные ограничения

- **Сохраняй monorepo**: `apps/web` + `apps/api` + `packages/shared` + `packages/contract-tests`. Не внедряй вторую несовместимую систему авторизации или БД.
- Используй TypeScript end-to-end, строгие типы, DTO/Zod валидацию, типизированные API-контракты, явную обработку ошибок.
- На dev оставить SQLite, но спроектировать документированный путь миграции к PostgreSQL для production, без потери данных и с обратимыми миграциями где возможно.
- Индексы по owner/created_at/cursor, транзакции на связанных изменениях, уникальные ограничения, защита от дублирования запросов.
- Для больших файлов / media: storage abstraction, local dev adapter, production S3-compatible adapter. Нельзя хранить бинарные видео в SQLite.
- Для фоновых задач: отдельный worker/очередь, повторные попытки и идемпотентность; Redis и внешние сервисы — через env и docker compose только при реальной необходимости.
- WebSockets: проверка авторизации и ACL не только на REST, но и при connect/join/event.
- Все секреты через env, обновить `.env.example` без реальных ключей; никогда не коммитить `.env`, токены или базы с персональными данными.
- Сохраняй совместимость существующих REST контрактов, когда это возможно; при изменениях добавь миграции и адаптацию UI.

## 4. Как ИИ должен работать: автономно, итерациями

1. Сделай **аудит кода**, а не только Markdown. Создай `IMPLEMENTATION_AUDIT.md` с таблицей: функция → frontend → endpoint → таблицы → permission tests → текущий статус `verified/partial/missing/blocked`.
2. Запусти `npm ci`, `npm run test:types`, `npm run build`, `npm run test:web`, `npm run test:api`, `npm run test:contract`. Зафиксируй реальный baseline и ошибки, ничего не придумывай.
3. Разбей работу на небольшие **вертикальные срезы**. Каждый срез: schema/migration → API/ACL → frontend → realtime (если нужно) → unit/integration/contract/e2e тесты → документация.
4. Начни с критических проблем (безопасное восстановление аккаунта, уязвимости зависимостей, реальные ACL). Затем доведи мессенджер, медиа/клипы, группы, звонки, музыку, поиск, маркет, админку и polish дизайна.
5. После каждого среза выполняй все перечисленные проверки. `npm run test:e2e` используй при установленных браузерах Playwright; иначе запиши чёткую причину блокировки.
6. Создавай миграции для изменённых данных; обеспечь данные для тестовых двух пользователей; никогда не используй реальных пользователей в фикстурах.
7. Обновляй `FEATURE_MATRIX.md`, `PROGRESS.md`, `TEST_REPORT.md`: что реально сделано, какие команды запускались, что осталось, какие провайдеры нужны.
8. Если интеграции требуют недоступных ключей/оборудования — реализуй интерфейс провайдера, локальный мок **только для dev/test**, а продакшн-функцию помечай `blocked`. Не заявляй, что платежи, push, TURN или трансляции «полностью работают» без проверки.
9. Если достигнут лимит контекста/времени, оставь проект в собираемом состоянии и запиши точную следующую задачу в `PROGRESS.md`, не замещая реализацию обещаниями.
10. НЕ ОСТАНАВЛИВАЙСЯ на создании документации. Главный результат — работающие изменения кода, тестов и миграций.

## 5. Рекомендуемый порядок поставки

| Этап | Инкремент | Definition of Done |
|---|---|---|
| P0 | Аудит, безопасность, auth/recovery, ACL, baseline | Запущены тесты, закрыты критические риски, известны реальные пробелы |
| P1 | Современный VK-like дизайн на всех текущих экранах | Полностью рабочая навигация на desktop/mobile, нет фальшивых кнопок |
| P2 | Мессенджер production-ready | Два пользователя обмениваются файлами и сообщениями realtime, ACL, reconnection |

| P4 | Группы, каналы, поиск, уведомления | Роли, реальные подписки, результаты поиска только по доступному контенту |
| P5 | Звонки, музыка, маркет | Работают на реальных инфраструктурных интеграциях или честно blocked |
| P6 | Админка, anti-abuse, observability, PWA, доступность | Модерация проверена, логирование без персональных секретов, полный regression suite |

**Важно:** это план, а не утверждение, что всё уже сделано.

## 6. Обязательные сквозные сценарии при приёмке

- Пользователь A регистрируется, пользователь B регистрируется; оба входят без подтверждения email при dev-настройке и не видят приватные данные друг друга.
- A отправляет заявку B, B принимает; друзья видят friends-only пост, посторонний C — нет; прямой API запрос от C тоже запрещён.
- A создаёт пост с фото/опросом, B реагирует и отвечает; после перезапуска данные остаются, уведомления появляются корректно.
- A и B общаются в двух браузерах в real-time; нельзя прочитать сообщения третьему участнику.
- A создаёт сообщество, назначает модератора, публикует пост, модератор может разрешённые операции, случайный пользователь не может.
- Загрузка запрещённого MIME/слишком большого файла отклоняется на backend и отображает понятное сообщение на frontend.
- При отсутствии конфигурации TURN, S3, push, payment система не падает: показывает корректную ошибку/отключённую функцию, без фиктивного успеха.
- Проверить keyboard/mobile usability, светлую/тёмную темы и отсутствие ошибок консоли.

## 8. Что считать результатом

Успех — не «все галочки» и не макет. Нужны реальные кликабельные страницы, работающая БД, авторизация, роли, безопасное API, загрузки, realtime, стабильная мобильная версия, тесты и запуск на чистой машине.

**Начни прямо сейчас с аудита репозитория, устрани P0, затем реализуй максимально полный следующий вертикальный срез и проверь его. Продолжай по плану с реальными коммитами.**
